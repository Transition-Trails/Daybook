# Worldsmith — Wave 3, step 16

Extract one shared readiness definition. This is the first of four structural steps, and it must come
before any further readiness change — correcting the arithmetic in one of six copies just moves the
disagreement around.

Read this whole page before editing. **The six implementations are not six copies of one thing** —
that assumption is what makes this look like a mechanical de-duplication, and it isn't.

---

## What is actually there

Four implementations score **a spec's completeness**. Two score **a compile run's outcome**. They
share a name and nothing else.

| # | Where | Function | Scores |
| --- | --- | --- | --- |
| 1 | `routes/worldsmith-editorial.ts:121` | `computeReadinessScore(spec)` | spec completeness |
| 2 | `NewSpecFlow.tsx:133` | `computeSectionScore(section, form)` | spec completeness, per section |
| 3 | `NewSpecFlow.tsx:138` | `computeOverallScore(form)` | spec completeness, all sections |
| 4 | `SpecEditor.tsx:86` | `getChecks(spec)` | spec completeness |
| 5 | `WorldSmithCompiler.tsx:2262` | `calcReadiness(result, prov, preflight)` | **compile run outcome** |
| 6 | `WorldSmithCompiler.tsx:4611` | `calcReadinessFromRun(run)` | **compile run outcome** |

**Extract 1–4. Leave 5 and 6 alone.** A spec's completeness ("has this been authored") and a run's
outcome ("did this compile cleanly") are different questions with different inputs — one reads spec
fields, the other reads a compile result, provenance and preflight. Folding them together would
produce a single function with two unrelated argument shapes and no meaning. If they need work, that
is its own step, and it is not this one.

So step 16 is: **one shared check list, three consumers.**

## Three problems the extraction has to resolve

Do not port these forward. Each currently exists in more than one copy, and the point of extracting
is to fix them once.

### 16a — The thresholds disagree, three ways

| Consumer | Bands |
| --- | --- |
| Server `derivePipelineStatus` | `canon_clear` ≥ 60 · `payload_ready` ≥ 30 |
| `NewSpecFlow` sidebar | Compile-ready ≥ 80 · Near complete ≥ 50 · In progress below |
| `SpecEditor` | publish button enabled at ≥ 30 |

Same underlying number, three different verdicts. A spec reading 55 is "Near complete" in the
creation flow, `canon_clear: false` on the server, and publishable in the editor. **Pick one band set
and put it in the shared module.** I would use the server's, since it is the one that gates
`derivePipelineStatus`, but the important thing is that one exists.

Note Wave 1 removed a check, so the server denominator moved from 18 to 17 while these bands stayed
where they were. Recalibrate deliberately as part of this step — that is the debt WAVE2.md told you
not to pay early, and this is where it comes due.

### 16b — Two checks can never fail

Both of these inflate every score by a fixed amount, in two separate files:

```js
// NewSpecFlow.tsx — canonDependency defaults to "None", which is truthy
{ label: "Canon dependency set", done: !!f.canonDependency },

// SpecEditor.tsx — the comment says "always set"
{ label: "Canon dependency set", done: true },
```

Delete the check. A field with a non-empty default is not evidence of authoring. Deleting it moves the
denominator again, which is another reason 16a and 16b belong in the same commit.

### 16c — `canon_clear` and `payload_ready` are named for conditions they don't test

The server derives both from the aggregate percentage. So `canon_clear` can be reported for a spec
whose canon checks all failed, as long as enough unrelated checks passed. In the shared module,
**expose the canon and payload conditions directly** and let `derivePipelineStatus` read those booleans
rather than thresholding an average.

## The correct canon condition already exists — twice

Both client implementations write it right:

```js
// NewSpecFlow.tsx and SpecEditor.tsx agree
done: f.canonDependency === "None" || f.canonRecordIds.length > 0
```

Wave 1 fixed the server to match. Use this form in the shared module; it is the version three of the
four consumers already expect.

## Two magic values to name while you are in here

- **`length > 30`** on payload content, in the server, `NewSpecFlow` and `SpecEditor` — three copies of
  an unexplained constant. Name it (`MIN_PAYLOAD_CHARS`) so it stops being folklore.
- **`promptPayload.includes("shared_prompt") || includes("asset_role")`** in `NewSpecFlow` — a
  substring test on raw payload text, standing in for "is this payload structured". You now have a
  real parser (`parsePayload`) and Wave 1 made the validator return its normalized output. Use it, or
  drop the check; a substring match on prose is not a structural claim.

## Shape of the shared module

```
lib/worldsmith/readiness.ts   (or wherever both server and admin can import from)

  export const MIN_PAYLOAD_CHARS = 30;
  export const BANDS = { canonClear: 60, payloadReady: 30 };

  export interface ReadinessCheck {
    id: string;            // stable — tests and UI reference this, not the label
    label: string;         // display text
    section: SectionId;    // "identity" | "creative" | "canon" | "payload" | "review"
    done: boolean;
  }

  export function readinessChecks(spec: SpecLike): ReadinessCheck[];
  export function readinessScore(checks: ReadinessCheck[]): number;
  export function sectionScore(checks: ReadinessCheck[], section: SectionId): number;
  export function canonClear(checks: ReadinessCheck[]): boolean;   // reads the canon checks
  export function payloadReady(checks: ReadinessCheck[]): boolean; // reads the payload checks
```

Three things this shape buys you, all of which the current copies lack:

- **`section` on every check** means `NewSpecFlow` gets its per-section scores from the same list as
  everyone else, instead of owning a parallel `SECTIONS` array.
- **A stable `id`** means a test can assert a specific check without matching display prose.
- **`canonClear` / `payloadReady` as functions over the checks** is what fixes 16c — the names finally
  describe what they measure.

`SpecLike` needs to accept both a persisted spec row and `NewSpecFlow`'s in-progress `FormState`.
They carry the same fields under different casing conventions; normalize at the boundary rather than
branching inside the checks.

## Verify

1. **One number, three surfaces.** Open the same spec in `SpecEditor`, and compare against the server's
   stored `readinessScore` and what the readiness board shows. All three match.
2. **A section score is consistent with the whole.** In `NewSpecFlow`, a form where every section reads
   100% must produce an overall of 100.
3. **The tautology is gone.** A brand-new empty form scores strictly lower than it did before this
   change (it was previously credited for `canonDependency` defaulting to `"None"`).
4. **`canon_clear` means canon is clear.** A spec with high overall completeness but zero canon records
   on a `Canon Defining` dependency reports `canon_clear: false`.

## Two things I noticed in `NewSpecFlow` that are not step 16

Neither is a readiness problem, both are worth a look while the file is open. **Do not bundle them
into this commit.**

- **A check in section 5 measures a field only editable in section 4.** "Prompt modules linked" sits in
  the Review section's checks, but `promptModuleIds` is set in the Payload section. So the Review
  section's own score can never reach 100 from its own form, which reads as a stuck progress
  indicator.
- **An `onFocus` prop is threaded through four section components and never passed at the call sites.**
  There is also a `{/* Section content + contextual co-write rail */}` comment with no rail rendered.
  Looks like a co-write feature that was started and left — decide whether to finish or remove it.
  (Also: `ReviewSection` renders a two-column grid containing one field, leaving half the row empty,
  and the sidebar uses **Playfair Display**, which is not in the Daybook system.)
