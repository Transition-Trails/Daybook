# Replit task — colour tokens, round 2: the guard does not guard

The nine mapped files from `REPLIT-ADMIN-TOKEN-DRIFT.md` are correct. `--admin-slate` is in
`index.css:94`, the four `build/` steps read it, `ProductRecipes.tsx` is clean of the cool-grey
literals, and `test/admin-colour-tokens.test.ts` exists. That part is done.

But the guard only catches the *shape* of the problem I happened to name, not the problem. And
running the wider search turned up roughly thirty more files carrying the same colours in a
different shape.

---

## 1. The regex only sees named constants

```ts
/const\s+(?:PAPER(?:_TINT)?|BORDER|MUTED)\s*=\s*["'`](?:#[\da-f]{3,8}|hsla?\([^)]*\)|rgba?\([^)]*\))["'`]/gi
```

This fails a file only if it declares a constant **named exactly** `PAPER`, `PAPER_TINT`,
`BORDER` or `MUTED`. It passes on every other way of writing the same hardcoded colour:

```ts
const T = { navy: "#1B2A4A", clay: "#C87560", slate: "#4A6080", muted: "#7A8FA6" };  // passes
<div style={{ borderColor: "#E7E0D7" }}>                                             // passes
className="border-[#E7E0D7] bg-[#FAF8F3]"                                            // passes
const CARD = "#FFFDF9";                                                              // passes
```

So the brief's acceptance criterion — *"the guard fails if someone reintroduces one"* — is not
met. Renaming a constant defeats it.

Replace it with a scan for **raw colour values anywhere** in `pages/**` and `components/**`:
hex literals, `hsl()`/`hsla()`, `rgb()`/`rgba()`, in string literals, style objects, and
Tailwind arbitrary-value brackets (`bg-[#...]`, `border-[#...]`, `text-[#...]`). Then subtract
the allow-list. Report the count it finds before you start fixing, so we can see the real size.

## 2. The allow-list is not connected to anything

```ts
it("keeps every raw-colour exception documented with a reason", () => {
  for (const exception of documentedRawColourAllowList) {
    expect(exception.scope).not.toBe("");
    expect(exception.reason).not.toBe("");
  }
});
```

This asserts that three hand-written strings are non-empty. It always passes, and it does not
exempt anything from the actual scan — the scan never consults the list.

Make the allow-list functional: each entry needs a **file glob or path** plus a reason, and the
scan skips matches inside allow-listed scopes. An entry that no longer matches any file should
fail the test, so the list cannot rot.

## What to do, in order

The standing instruction is **make the colour consistent** — do not stop to ask about individual
values. Every raw colour in `pages/**` and `components/**` either maps onto an `--admin-*` token
or earns an allow-list entry with a written reason. Nothing stays raw and undocumented.

1. **Rewrite the guard first** (items 1 and 2), with the allow-list wired in. Run it. Report the
   total count and a per-directory breakdown — for the record, not for approval. Then continue.
2. **Fix all of it**, using this mapping:

| Raw value | Token | Risk |
|---|---|---|
| `#4A6080` | `var(--admin-slate)` | none — same hex |
| `#E7E0D7` | `var(--admin-border)` | negligible |
| `#8A7B6A` | `var(--admin-faint)` | negligible |
| `#7A8FA6` | `var(--admin-muted)` | **visible** — cool to warm, 4 files |
| `#FAF8F3` / `#FFFCF8` | `var(--admin-card)` or `--admin-card-subtle` | slight — preserve layering |
| any other hex/hsl/rgb the scan finds | nearest `--admin-*` token | judge per site |

   Where the nearest token is genuinely wrong for a site, allow-list it with a reason instead of
   inventing a token. Add a new token only if the same unmapped colour appears in **three or
   more** files with the same role — and say which you added.
3. Screenshot before/after for the four `#7A8FA6` files and any site where you judged a swap
   rather than matched one, so the visible changes are reviewable in one place.
4. Leave `WorldSmithHome.tsx` alone — its arbitrary status palette stays out of scope, but the
   new allow-list should name it explicitly rather than relying on the old test's inert array.

One note on scope: `planners/InkEditor.tsx` uses `#4A6080` for toolbar text and `#1B2A4A`,
`#C87560`, `#000000` as **ink colours the user draws with**. Those are product data, not chrome.
Swap the toolbar chrome; leave the pen palette as literal values and allow-list it.
