# Worldsmith — Wave 3, step 17

Point the inheritance resolver at Postgres. This is the largest change in the plan and the one that
makes locally-authored fields reach a prompt at all.

Do **not** start this until step 16 is merged (it is). Read the whole page first — the sequencing
inside the step matters more than the code.

---

## The problem, precisely

`resolveInheritanceChain` is keyed by a **Notion page ID**, and fetches every governed record from
Notion via `getPage`:

| Record | Source today |
| --- | --- |
| Production specification | Notion (`getPage(specId)`) |
| Style guide | Notion (`getPage` + `getPageText`) |
| Component specification | Notion (`getPage` + `getPageText`) |
| Prompt modules (+ 1 level of dependencies) | Notion, per module |
| Canon records | Notion — **name + status only** |
| World Bible (4 fields + rules) | **Postgres** — the only local read |
| `ws_*` Editorial Suite tables | **never read** |

Two consequences you are living with:

1. **A field that exists only in the local DB cannot reach a prompt.** Not "is ignored" — the code
   never looks there. This is the thing you noticed when Notion became painful to maintain.
2. **`extractProductionSpec` reads ~40 fields through guessed-property fallback chains** —
   `extractRichText("Production Item") || extractTitle("Name")`, `"Volume" || "Volume / Collection"`,
   `"Canon Records" || "Canon"`. That is code not knowing its own schema. There is even a leftover
   `logger.info` dumping every property key on a payload page so someone could see what was there.

The Editorial Suite already declares Postgres authoritative and Notion a publication target. The
compiler is the last component that disagrees.

---

## Do it in four commits, not one

The temptation is one big swap. Resist it — you lose the ability to attribute a regression, and a
compile pipeline is exactly where you want that ability.

### 17a — Add a local resolver alongside the Notion one. Change nothing else.

New function, new file, no call sites touched:

```
lib/worldsmith/inheritance-resolver-local.ts

  export async function resolveInheritanceChainLocal(
    specId: string,          // ws_production_specs.id — a UUID, not a Notion page id
  ): Promise<InheritanceChain>
```

Return the **same `InheritanceChain` shape** the Notion resolver returns. That is the whole trick of
this commit: downstream code (`validator`, `prompt-compiler`, `payload-generator`,
`spec-preview-service`) must not be able to tell which resolver produced its input.

Read from `ws_production_specs` and follow its real foreign keys to `ws_style_guides`,
`ws_component_specs`, `ws_prompt_modules`, `ws_canon_records`, `ws_collections`, `ws_volumes`. No
property-name guessing — these are typed columns.

**Done when:** a test calls both resolvers for one spec that exists in both systems and asserts the
two chains are structurally equal, field by field.

### 17b — Fetch canon record bodies in the local resolver

This is step 18 from the plan, and it belongs here rather than after, because the local row already
carries the data. `resolveCanonRecord` currently extracts name and status; the local equivalent
should carry `emotional_register`, `sensory_clauses`, `summary`, `details`, `record_type`, `status`.

Then emit them in `CANON POLICY` in `prompt-compiler.ts` — each record's register and sensory clauses
beneath its name, rather than a bare list of names.

**Done when:** editing a canon record's sensory clauses changes the compiled prompt *and* changes the
prompt hash. Today it changes neither.

### 17c — Switch the orchestrator over, behind a flag

```js
const chain = USE_LOCAL_RESOLVER
  ? await resolveInheritanceChainLocal(spec.id)
  : await resolveInheritanceChain(spec.notionPageId);
```

Environment flag, default **on** in dev and **off** in production until you have compiled a handful
of real specs both ways and compared the prompts. Keep the flag for one release, then delete it and
the Notion resolver together — a permanent flag is a permanent fork.

**Watch:** `POST /production-packages` and the spec-preview service both enter the pipeline with a
Notion page id today. Both need to accept a local spec id. Grep for `specPageId` — the name itself
encodes the assumption.

### 17d — Fix the World Bible join while you are in here

From step 19, but it becomes trivial once the chain is local:

```js
// today — detaches silently on rename, zero rows leaves worldBible undefined
WHERE lower(name) = lower(spec.world)

// instead
WHERE id = spec.worldId
```

And treat **zero rows as a first-class warning**, not a silent success. Today
`WORLD_BIBLE_FETCH_ERROR` only fires when the query *throws*. When it returns nothing, the compile
succeeds with no visual palette, no prose voice, no material world and **no world rules** — a
clean-looking compile stripped of its entire aesthetic grounding.

**Done when:** a spec whose world cannot be resolved fails or warns loudly, and renaming a world does
not change what compiles.

## What this buys you

- Fields you add in Replit start working, with no Notion column required.
- Canon bodies become compilable (17b) — the single biggest quality change available.
- Compiles stop depending on Notion being reachable, and stop being rate-limited by it.
- ~40 guessed property names collapse into typed columns.
- Renaming a world stops detaching its Bible.

Notion keeps the job it is good at — a readable published archive — through the publish adapter that
already exists. **Nothing about this step removes the Notion sync.** It inverts the direction: Notion
becomes an output, which is what the Editorial Suite schema always claimed.

---

## Two things NOT to do here

- **Do not fold the spec-preview service into this commit.** It re-derives board data from Notion with
  its own ~30 fallback chains, and it should instead receive the compiled `sectionRecords` directly.
  That is real work, it is step 19, and bundling it means a board regression and a prompt regression
  arrive in the same commit.
- **Do not change the prompt-module routing yet.** Modules are still routed by matching substrings in
  their names (`includes("world")` / `"style"` / `"aesthetic"`), so renaming a module silently changes
  the compiled prompt. Also step 19. Fixing it needs a `section` enum on `ws_prompt_modules` and a
  migration — a different kind of change from this one.

---

## Expect these, they are correct

- **Every prompt hash changes** once 17b lands, because the prompts genuinely changed. Anything keyed
  off an old hash regenerates once.
- **Boards regenerate** on next compile — `TEMPLATE_VERSION` is now shared (Wave 2), so a prompt change
  alone will not force it, but a changed spec will.
- **A spec present in Notion but not in Postgres will stop compiling.** That is the point, but find out
  now rather than mid-release: count `ws_production_specs` rows against the Notion database before
  flipping 17c's flag in production.

## Test first

```
inheritance-local.test.ts
  · both resolvers produce structurally equal chains for the same spec        (17a)
  · a canon record's emotional_register and sensory_clauses appear in
    the compiled CANON POLICY section                                        (17b)
  · a spec whose worldId matches no world row produces a blocking warning,
    not a successful compile                                                 (17d)
  · a compile succeeds with the Notion client stubbed to throw               (17c)
```

That last one is the real acceptance test for this step: **if the compile still works with Notion
unreachable, the migration is done.**
