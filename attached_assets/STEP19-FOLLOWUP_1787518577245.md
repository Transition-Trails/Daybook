# Worldsmith — step 19 follow-up

Step 19 landed well. Three loose ends, none large. The first is the only one that can quietly
change output, so do it first.

---

## 1 — The `section` column has no migration and no backfill

`lib/db/src/schema/worldsmith-editorial.ts` L159 declares:

```ts
section: text("section").notNull().default("general"),
```

But no script in `scripts/src/` adds that column, and `ci.yml` (L219–229) does not run one. Two
problems follow.

**An existing database may not have the column.** A Drizzle schema declaration is not a migration.
Any environment whose `ws_prompt_modules` table predates this change will throw on the first
local-path compile.

**Where the column does exist, every existing row is `'general'`.** Before step 19, a module named
"World Materials" routed to the world section by title match. Now it routes to `general`, because
nothing backfilled it. No error, no warning — the prompt just quietly loses a section. This is the
exact drift the handoff's backfill step existed to prevent.

**The fix — one script, `scripts/src/migrate-prompt-module-section.ts`,** following the same shape as
`migrate-worldsmith-compiled-sections.ts`:

```sql
ALTER TABLE ws_prompt_modules
  ADD COLUMN IF NOT EXISTS section text NOT NULL DEFAULT 'general';

UPDATE ws_prompt_modules SET section =
  CASE
    WHEN lower(name) LIKE '%style%'     THEN 'style'
    WHEN lower(name) LIKE '%aesthetic%' THEN 'style'
    WHEN lower(name) LIKE '%world%'     THEN 'world'
    ELSE 'general'
  END
WHERE section = 'general';
```

Two details that matter:

- The `CASE` order must be **style / aesthetic before world**, matching
  `legacyPromptModuleSection()` in `inheritance-resolver.ts` L296–300. A module called "World
  Aesthetic Notes" matched `style` under the old code; the backfill has to agree or that module moves.
- The `WHERE section = 'general'` guard makes it safe to re-run and stops it overwriting any section
  an author has already set deliberately.

Then add it to `ci.yml` beside the other migrations, and register the script in the `@workspace/scripts`
package.

**Done when:** a compile of a spec whose modules were routed by title produces the same prompt it did
before step 19.

## 2 — Two Wave 2 step 14 items that did not land

Both in `inheritance-resolver.ts`, Notion path.

**The version error names the wrong version.** `MISSING_PAYLOAD_VERSION` currently reads:

> "Payload Version is blank. Set it to PP-1.0 on the linked Prompt Payload record…"

The payload generator refuses anything other than PP-2.0 and errors with "Payload Version must be
PP-2.0." An operator who follows the first message lands directly on the second. Say PP-2.0, and
mention PP-1.0 only as the legacy value that still compiles.

**A debug log is still shipping.** In the Prompt Payload resolution block:

```ts
logger.info({ promptPayloadId, propertyKeys: Object.keys(pp) }, "WorldSmith: Prompt Payload page properties");
```

That was written to discover what Notion property names actually existed. It has served its purpose.
Drop it to `logger.debug` or remove it.

## 3 — Confirm one behavior change from step 16

Not a bug — a decision that needs your sign-off, because it shipped as a side effect.

`payloadReady` now requires **all four** payload checks, and one of them is "at least one prompt
module linked". `SpecEditor` L271 gates the publish button on `payloadReady`. So **a spec with no
prompt modules can no longer be published**, where previously the gate was a readiness score of 30.

That may be exactly right — a spec with no modules is arguably not ready. But it is stricter than the
gate that existed before step 16, and it was not asked for. Either confirm it, or drop
`prompt-modules` out of the `payloadReady` set and leave it as a visible check that does not block.

## After this

The fix plan is complete. What remains is Wave 4 — three product decisions, no code:

- **Spec immutability.** Correcting a typo in Design Intent currently means creating a new spec. The
  code states this deliberately; confirm it is still what you want as the daily operator.
- **`worldRules` permission level.** Store staff can currently rewrite the hard negatives appended to
  every prompt. Daybook's convention elsewhere is staff draft, owners publish.
- **Structured typography field.** The font picker appends prose into four compiled fields, so
  "Available variants: 4" currently reaches an image model.

And Phase 2 generation, which carries its own two known items: the prompt hash needs its
provider/model/settings fields actually passed, and the two generation paths
(`canon-records/generate-image` vs `production-packages`) need reconciling.
