# Replit task — split Product recipes into three views

Reference design: `Daybook Product Recipes.dc.html` (three views behind a segmented control in
the page header). Do not copy that file's code — it is a design artifact. Implement the spec
below against `pages/super/ProductRecipes.tsx` and the existing `recipesApi`.

Current page is 35KB doing four jobs at once: recipe list, e-ink export profiles, "what a recipe
defines" explainer, and release schedule. Three of those become their own thing.

Work in order. Phase 0 first — there are three live bugs.

---

## Phase 0 — Bugs in the current page

### 1. `RecipeDrawer`'s create path is unreachable dead code

```ts
const [editing, setEditing] = useState<ProductRecipe | null | "new">(undefined as any);
const drawerOpen = editing !== undefined && editing !== null && editing !== "new" as any;
```

`RecipeDrawer` treats `recipe === null` as "create new" — but `drawerOpen` requires
`editing !== null`, so the create branch can never render. Meanwhile "New recipe" navigates to
`/super/recipes/new` (`NewRecipe.tsx`, 54KB). So there are two create surfaces, one of which is
unreachable, and roughly a third of `RecipeDrawer` is dead.

Also `editing !== "new" as any` — the `as any` is on the string literal and does nothing. And
`useState(undefined as any)` against a type that does not include `undefined` defeats the type.

Fix: one state, one drawer, honest types.

```ts
type DrawerState = { mode: "closed" } | { mode: "create" } | { mode: "edit"; recipe: ProductRecipe };
```

The drawer handles both create and edit (Phase 2). Decide `NewRecipe.tsx`'s fate explicitly: if
the drawer covers it, delete the route and the file; if it does something the drawer cannot,
say what in a comment and keep it as the only create path. Do not leave both.

### 2. `dotLabel` is wrong every December

```ts
const isNext = rel?.month === now.getMonth() + 2;
```

In December `getMonth()` is 11, so this looks for month 13. In November it looks for 13 too.
No recipe matches, so "next month" silently never renders. Compare on absolute months:
`rel.year * 12 + rel.month === thisYear * 12 + thisMonth + 1`. Same bug class as the calendar
formula we already fixed in the generator — compare absolute month indices, never bare numbers.

### 3. The page redefines the design tokens, with different values

```ts
const INK = "hsl(221 46% 17%)";  const CLAY = "#C87560";
const PAPER = "hsl(38 65% 96%)"; const BORDER = "hsl(38 30% 88%)";
const MUTED = "hsl(216 15% 52%)";
```

`index.css` already has `--admin-ink`, `--admin-clay`, `--admin-paper`, `--admin-border`,
`--admin-muted`. These five locals disagree with them: `PAPER` is not `#F7F0E6`, `BORDER` is not
`#E7DCCB`, and `MUTED` is a **cool grey** in a system whose rule is that borders and muted text
are warm. This is precisely the drift the token block exists to prevent.

Delete all five constants. Use the CSS variables. Then grep the whole of `pages/` for
`const INK`, `const CLAY`, `const BORDER`, `const MUTED`, `hsl(216 15%` and `hsl(38 30%` and
report what else is carrying a private copy of the palette — fix those in the same pass if it is
a handful, list them if it is more.

While you are in there: `StatusBadge` and `TierBadge` are local reimplementations of the shared
`Pill` with their own colours and `rounded` (4px) corners instead of pills. Replace both with
`Pill`. `StatTile` duplicates the shared one. The page also renders its own `<h1>` header
instead of `PageHeader`, and uses `max-w-5xl` (1024px) instead of the 1120px container.

## Phase 2 — Recipes view

### Metric strip

Four cells in one bordered card, matching the dashboard strip: uppercase 10px label, Spectral
22px value, and a small note under the value instead of a fake delta. Notes carry meaning:

- Live recipes → `9` · "across 4 studios"
- In draft → `3` · "1 blocked" (clay `#A85B48`, weight 600 — this one is a warning)
- Ships next month → `1` · the recipe name
- Renewals citing new → the real number, or delete the cell

That last one is `stats.renewalsCitingNew` and it reads 0%. If it is not instrumented, do not
show a hero 0% — either wire it or cut the cell to three.

### Blocker banner

Above the filters, when any recipe fails validation: a single clay-left-border card naming the
recipe and the reason, clickable straight into its drawer. Today the `ci_bad_recipe` failure is
invisible on this page even though it breaks every deploy.

### Filters and table

Search over name and parts. Studio filter chips (All + the five studios). Right-aligned
"N of M recipes".

Grid `2.6fr 1fr .8fr .9fr 24px` — Recipe / Plans / Builds (right, mono) / Status (right) /
chevron. The Recipe cell is name + clay studio label on one line, parts joined by ` · ` on a
second line, both truncated. Uniform `12px 18px` padding on every row.

Row click opens the drawer. Delete the per-row "Edit →" chip — the row is the target.

Status: a live recipe whose release month is the current month shows **NEW** instead of LIVE.
That logic exists and is correct; keep it, but move it out of `RecipeRow` into a helper so the
schedule view can use the same rule.

### Recipe drawer — the six fields, review-first

460px, same scrim and shadow as the flags drawer. Header: kicker `Recipe · {studio}`, name in
Spectral 18px, status pill beside it.

Body, in this order:

1. **Blocking release** — only when the recipe has blockers. `#FDF7F4` on `#E8CFC7`, uppercase
   clay heading, one line per blocker with a `▲` mark. Derive these server-side from real
   validation, do not hardcode a list in the component. At minimum:
   - no parts list
   - `category` is not one of the known studio names
   - `physicalPath.prints` is true with no `impositionSheet`
   - no `release.month` or no `release.planTiers`
   - a decision card with a prompt but a missing option label or consequence
   - a Claude brief with asks but no `generates`
2. **Name & studio** — name is an input, studio is a select.
3. **Parts list** — chips. Selected parts read as filled chips; when empty, one dashed clay chip
   reading "no parts selected" with the count note "empty — this is what blocks release".
   Keep the full `ENGINE_REGISTRY` picker, but behind an "Edit parts" toggle — 36 chips is a
   wall when you opened the drawer to check the release month.
4. **Decision card** — the prompt as a header row, then the two options side by side, each label
   over its consequence. When unset, show the two cells with "The buyer has nothing to answer
   first."
5. **Physical path** and **Release** side by side, one line each in review mode.
6. **Claude brief** — asks list, then generates, on a `#FBF6EE` panel.

Footer: Save changes (navy), then Publish or Retire, then Cancel. **Publish is disabled while
blockers exist** and reads "Blocked". Retire replaces the browser `confirm()` with a proper
dialog — the repo already has `AlertDialog`.

`buildPayload` currently sends `decisionCard: undefined` when the prompt is empty, which on
PATCH may mean "leave it alone" rather than "clear it". Be explicit: send `null` to clear.

## Phase 3 — Schedule view

This is the renewal argument, so it is a calendar, not a list. **The finding is the empty month**
— a list sorted by date cannot show a gap.

Top row: a navy card stating the argument in one sentence, beside a 2×2 stat block — Shipped
this year, Scheduled, **Months with nothing** (clay when > 0), Longest gap in consecutive months.

Then a 12-row calendar for the year. Grid `.9fr 2fr .9fr .9fr` — month (mono 2-digit number +
name) / recipe name + studio / plans / state pill, right-aligned.

Row states:

| State | When | Pill | Row |
|---|---|---|---|
| Shipped | month < current | live green | normal |
| This month | month = current | clay | normal |
| Scheduled | future, status live | blue info | normal |
| Draft | future, status draft | amber | normal |
| **Nothing scheduled** | no recipe that month | clay | `background: #FDF7F4`, month name and "No recipe" in `#A85B48` |

The empty row's sub-line says what the gap costs: "A month a store renews for software it
already had." Row click opens that recipe's drawer; an empty row opens the create drawer with
the month prefilled.

A year selector belongs here (2026 / 2027) since recipes carry a year.

Below: a short "What a store sees when a recipe drops" card — in the studio picker, in the
email, at renewal. Three lines, keep them.

## Phase 4 — E-ink export profiles, own page

New route `/super/recipes/eink` (reachable from the segmented control). Move the whole section
off the recipes page.

**The device presets and the five rules are currently hardcoded arrays in JSX.** That means
adding a device or changing the contrast floor needs a deploy, and nothing else in the system can
read them. Move them into the database — an `eink_device_presets` table (name, trim width/height,
link support enum `full | partial | poor`, sell-guidance text) and the five enforcement rules as
config the export checker actually reads. The page then edits real rows. If that is too large for
this pass, say so and keep the arrays, but put them in one exported module so the checker and the
page share one source.

Layout:

- Explainer card, navy left border, with the "Inherited by every recipe" pill right-aligned.
  One sentence: it is not a studio and not a recipe.
- Device table, grid `1.4fr .8fr 2.4fr .9fr` — Device / Trim (mono) / How to sell it / PDF links
  pill, right-aligned. Green for full, clay for poor.
- Two cards side by side: **What the profile enforces** (five rules, 96px uppercase key beside
  the explanation) and **Listings that overclaim**.

That second card is new and it is the point of the page. Query live listings that claim
hyperlinked navigation while targeting a device whose profile marks links `poor`, and list them
with store and age. Kindle Scribe is the case that matters. Footer line: the profile cannot edit a
store's listing copy, it can only flag it — so this is a queue, and it should feed the dashboard
decision queue too (that condition is already specified in the dashboard brief).

## Phase 6 — Design-system drift, admin-wide

**Most of this phase has already shipped** via `REPLIT-ADMIN-TOKEN-DRIFT.md` rounds 1–3: the
private palette copies are gone, the cool greys are converged, `--admin-slate` exists,
`--admin-prototype-ink` is deleted, and `test/admin-colour-tokens.test.ts` guards it with
per-scope fingerprints. Do not redo that work.

What is left:

### 6a. Unpin line numbers from the colour fingerprints

`test/admin-colour-tokens.test.ts` builds each exception's fingerprint from
`` `${match.file}:${match.line}:${match.value}:${match.lineText.trim()}` ``. Because `match.line`
is in the input, **any** edit that shifts a line number inside an exempt scope fails the test
with a colour-drift message. Adding a paragraph of copy to `pages/shop/StorefrontHome.tsx` — a
change containing no colour — breaks `admin-colour-tokens`. That reads as flakiness and the guard
gets routed around.

Drop `match.line` from the fingerprint input; keep file, value, and trimmed line text. That still
catches a new colour, a changed colour, and a colour moved between files, while surviving line
movement. The sort already makes order irrelevant.

Then add the two missing affordances:

- `UPDATE_COLOUR_FINGERPRINTS=1 npm test` rewrites the `exceptionFingerprints` map in place, with
  the command noted in a comment above the map.
- On failure, print a **diff** — which raw colours were added, removed or changed inside that
  scope — not just a hash mismatch. The hash says something moved; the diff says whether it is
  drift or an intentional new semantic colour.

Also: `pages/super/WorldSmithHome.tsx` already matches the `pages/super/*.tsx` glob, so its own
entry can never fail the staleness check independently. Drop it, or narrow `pages/super/*.tsx` to
exclude it, so each entry owns a distinct set.

### 6b. Report the worldsmith-editorial card layering

`#FFFCF8` and `#FAF8F3` were both used as card backgrounds in `super/worldsmith-editorial/` and
are now gone from the codebase, but what replaced them was never reported. `#FFFCF8` is a light
near-white (closer to `--admin-card`, `#FFFDF9`) while `--admin-card-subtle` is `#FBF6EE`, a warm
tint — so it is possible the lighter hex landed on the tinted token and inverted the layering.

Check each site. The raised surface takes `--admin-card`, the recessed one
`--admin-card-subtle`, regardless of which hex it started as. Say what you found and what you
changed.

### 6c. Still outstanding from the original sweep

These were never part of the colour work and are still open:

1. **One `Pill`, no local badges.** `StatusBadge`, `TierBadge`, and any other per-page status
   chip collapse into the shared `Pill` with tones `live / draft / info / warn / on / off`.
   Pills are 20px radius — not `rounded` 4px. Report every local badge you deleted.
2. **One `StatTile`, one `MetricStrip`, one `PageHeader`, one `DataTable`.** Pages that hand-roll
   any of these get switched over. If a page needs a variant, add a prop — do not fork.
3. **Container width.** 1120px content max everywhere except studio surfaces (which already opt
   out via `admin-content__inner--studio`) and the owner home at 1000px. `max-w-5xl` and
   `max-w-4xl` in admin pages are drift; replace them.
4. **Radii and shadows** come from the documented set only: 7–9px controls, 12px tiles, 14px
   content cards, 20px pills; the four documented shadows. `shadow-2xl` on the recipe drawer is
   not one of them — the drawer shadow is `-10px 0 34px rgba(27,42,74,.2)`.
5. **Fonts by role, not by guess.** Spectral for headings and numerals, Instrument Sans for body
   and UI, Space Mono for timestamps, counts, IDs and numeric table cells. Numeric table cells
   are mono **and right-aligned** — `tabular-nums` on a sans face is not the same thing.
6. **`confirm()` and `alert()`** are not part of the system. The repo has `AlertDialog`; use it.
   Grep for both and report.

## Decisions already made — apply these

Angela has ruled on four open questions. Treat them as settled.

1. **Platform catalog authoring is canonical.** `super/CatalogAuthoring.tsx` + `GlobalCatalog.tsx`
   are the real surfaces; the legacy catalog list pages (~190KB) get deleted. Before deleting:
   produce a one-page inventory of what the legacy pages can do that the new ones cannot, so
   nothing is lost silently. Then delete in one pass, not gradually.
2. **Journal Studio is promoted to the store console.** It is a real studio with recipes
   (junk journal kit, memory book, solo journaling game). Give it a proper home alongside the
   others; do not leave it as a 41KB orphan.
3. **Daybook Ink is parked.** Keep it flag-gated, stop building on it, and remove the second
   mount point so there is exactly one. Do not delete it.
4. **Google sync + Calendar has a home.** Both now live under Settings at
   `/super/settings/google` and `/super/settings/calendar`. Nothing further needed.

Also settled since this brief was written: the `/daybook/` route prefix is **gone from the admin
nav** — all seven pages moved to `/super/` with permanent redirects. The only remaining
`/daybook/` routes are the legacy *catalog* pages, which decision 1 above deletes.
