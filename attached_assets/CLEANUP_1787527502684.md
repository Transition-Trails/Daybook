# Worldsmith — cleanup pass

Everything left on the Worldsmith board, in one place. Nothing here is architectural — it is the
residue after four waves: two policy decisions the code currently answers by default, one UX gap, and
a set of small items that never had a home.

Order below is the order to do them in. The two decisions come first because they are cheap and
because the rest is easier to review once they are settled.

---

## 1 — Say why the publish button is disabled

**Where:** `SpecEditor.tsx` around L271, where publish is gated on `payloadReady`.

Publishing now requires at least one linked prompt module. That policy is confirmed and correct, but
the button gives no reason for being disabled, so a stricter gate reads as a broken control. This is
the same failure the read-only fields had before Wave 2 — the UI knows something the user does not.

Show the blocking check by name. Ideally list any failed `payload`-section checks:

> Link at least one prompt module to publish.

**Done when:** hovering or reading near a disabled publish button tells you exactly which check to
satisfy.

---

## 2 — Split the world-rules permission (decided)

**Where:** `PATCH /v1/worldsmith/worlds/:id`, currently `requireStoreAccess("store_staff")`.

World rules are the hard negatives appended last to every compiled prompt — the constraints no record
can override. Store staff can currently rewrite them. Daybook's convention everywhere else is staff
draft, owners publish.

**Decided: split the payload.** Staff may write `visualPalette`, `proseVoice`, `atmosphericNotes`,
`materialWorld` and `typography`; only `store_owner` may write `worldRules`. World rules are the only
field where one edit silently changes every future image in the world, and that asymmetry deserves a
different permission from prose.

Implementation notes:

- Enforce on the **server**, in the `PATCH /v1/worldsmith/worlds/:id` handler — not by hiding the field
  in the UI. Hiding a control is not an authorization boundary, which is the reasoning the store-access
  memo already records for the rest of Worldsmith.
- Reject rather than silently drop: if a `store_staff` request includes `worldRules`, answer **403**
  with a message naming the field. A silently ignored write is worse than a refusal — the author
  believes the rule is in place.
- The UI should render `worldRules` read-only for staff with a short reason, so the boundary is visible
  where someone would try to type. Same principle as the SpecEditor fields and the publish button.
- Add a test for both directions: a staff PATCH carrying `worldRules` is refused; the same PATCH
  carrying only the five prose fields succeeds.

**Done when:** a `store_staff` PATCH including `worldRules` returns 403 naming the field, the same
PATCH without it succeeds, and the decision is recorded in a memory file.

## 3 — Decide: are production specs really immutable?

**Where:** enforced by the 405 on `PATCH /v1/editorial/specs/:id`, plus SpecEditor's Lock chip and
banner.

Correcting a typo in Design Intent currently requires creating a whole new spec. The code states this
deliberately — it is a position, not an oversight — but it was decided when Worldsmith was expected to
be a store-facing product with an audit-trail requirement. You are now the daily operator.

- **Keep it.** Immutability is genuinely valuable for a record that anchors compiled artifacts. Pair
  it with a "duplicate this spec" action so correcting a typo is two clicks rather than re-entry.
- **Narrow it.** Allow PATCH on the creative fields (design intent, narrative purpose, required
  content, review criteria) while keeping identity and payload locked. Keeps the audit value where it
  matters — what was compiled — and removes the friction where it does not.

I lean toward narrowing, but this is a judgment about your own workflow: how often do you actually hit
it? If the answer is "rarely," keep it and add the duplicate action.

**Done when:** either a `POST /specs/:id/duplicate` route exists, or a narrowed PATCH accepts the four
creative fields and rejects everything else with a message naming what is locked.

## 4 — Small items with no home

These accumulated across the audit and were never worth their own commit. Batch them.

- **`normalizeNotionId` duplicates server logic** — `WorldSmithCompiler.tsx` L30, by its own comment.
  Import the server helper or move it to a shared module.
- **Split localStorage namespaces** — some keys use `worldsmith:`, others `ws:editorial:`. Pick one.
- **`RECOMMENDATION_CODES` is declared at L3946 but used from L2310** — hoist it to the top of the
  module with the other constants.
- **`CostEstimateCard` (L3219) presents four hardcoded dollar literals as a calculation**, summed into
  "Estimated Total", with its own comment admitting they are static. `SPEC_PREVIEW_QUALITY` can be set
  to `hd`, changing real cost without changing the display. Either label it "indicative" or derive it
  from the provider and quality actually configured. Same issue in prose at L3075: "Estimated effort:
  Under two minutes."
- **`BANDS.canonClear` is dead** — verdicts come from booleans since step 16. Remove it, or comment why
  it is retained. `BANDS.payloadReady` survives only as a color threshold in two files; say so.
- **Four detail crops still include letterbox bars** (finding 18) — `DETAIL_CROP_SOURCE_RECTS` are
  computed against the concept-area constants, not the composited image box. Either compute from the
  real box or set `SPEC_PREVIEW_SIZE` to `1792x1024` to match the 1.19 area ratio. The env var already
  exists.
- **`referenceImageUrls` is scavenged and discarded** (finding 19) — the service collects up to four
  image URLs from Notion and the template never reads them. Confirmed an unlanded feature, not a
  regression. Either render the thumbnails or delete the scavenging; it currently costs round-trips for
  nothing.
- **The 4 MB guard downscales 2400→1400px** (finding 20), taking 8.5px board text to ~5px, silently,
  precisely on the richest boards. Compress rather than resize; if a downscale is unavoidable, record
  it on the audit row.

## 5 — One thing to leave alone

**A compile with dropped module dependencies still reports a clean "Compiled".** There is a 19 KB test
asserting the drop-and-continue behavior, so it is deliberate and should stay. The change worth making
is to the *reporting*, not the behavior — a distinct status such as "Compiled with omissions" so the
artifact is not indistinguishable from a complete one. That is a small piece of product design, not a
bug fix, and it belongs with Phase 2 rather than this pass.
