# Worldsmith — Wave 3, step 19 (the last of the plan)

Two changes, plus one small residue from Wave 2. After this, the fix plan is done and everything
left is Wave 4 decisions or Phase 2 generation work.

Step 17 already moved the preview service onto the local resolver — that was half of this step and
it is done. What remains is listed below.

---

## 19a — Route prompt modules on an explicit field, not on their names

**The problem.** `prompt-compiler.ts` decides where a module's content lands by matching substrings
in the module's *title*:

```js
// three places in the PP-2.0 path, plus the legacy path
name.includes("world")      // → world section
name.includes("style")      // → style section
name.includes("aesthetic")  // → style section
```

So renaming a module from "World Rules — Materials" to "Materials — World Rules" changes nothing,
but renaming it to "Material Standards" silently drops it out of the world section and into the
default bucket. Nobody gets a warning. A prompt quietly loses a section because someone tidied a
title.

It is also ambiguous today: a module called "World Aesthetic Notes" matches both `world` and
`aesthetic`, and which one wins depends on the order the conditions are evaluated.

**The change.**

1. **Migration** — add a `section` column to `ws_prompt_modules`:

```
section text not null default 'general'
  -- allowed: 'world' | 'style' | 'general'
```

Follow the existing migration-script pattern in `scripts/` and wire it into `ci.yml` like the other
15.

2. **Backfill using the current logic, once.** This is the important part — do not hand-assign:

```sql
update ws_prompt_modules set section =
  case
    when lower(title) like '%style%'     then 'style'
    when lower(title) like '%aesthetic%' then 'style'
    when lower(title) like '%world%'     then 'world'
    else 'general'
  end;
```

Reproducing today's behavior exactly means the backfill produces **no prompt changes at all**. Any
module that is in the wrong section afterwards was already in the wrong section — you can then fix
those deliberately, one at a time, and see each one's effect.

3. **Read the column** in `prompt-compiler.ts` (all three PP-2.0 sites and the legacy path) and drop
   the `includes()` checks. Carry `section` through the resolver's module rows.

4. **Expose it** on the prompt-module editor as a three-option select. It is a routing decision, so
   the author should be able to see and set it.

**Done when:** a test asserts that renaming a module does not change its compiled section, and that a
module with `section = 'style'` lands in the style section regardless of its title.

**Watch:** the legacy path has its own copy of these conditions. Grep for `includes("style")` and
confirm you have all four sites, not three.

## 19b — Have the preview service receive compiled sections

**The problem.** The service now reads from Postgres (good — step 17), but it still *re-derives* board
data with its own extractor rather than being handed what the compiler produced. Two independent
derivations of the same values, and nothing tests that they agree. When one drifts, the sheet a human
approves stops describing the prompt that was actually compiled.

This compounds with the invented-content behavior: a field that comes out empty in the board's
derivation gets a substituted default, so the board can show confident material notes for a prompt
that has none.

**The change.** Pass the compiled result into the service instead of re-deriving:

```js
// today (roughly)
const chain = await resolveInheritanceChainLocal(specId);
const boardData = extractBoardData(chain, ...);

// instead — accept the compiled output as an argument
export async function generateSpecPreview(opts: {
  specId: string;
  promptHash: string;
  sectionRecords: SectionRecord[];   // <- from compilePrompt
  ...
})
```

Then `extractBoardData` maps `sectionRecords` onto board zones rather than re-reading source records.
Where a section is genuinely absent, the board should show its "not specified" state — which now
exists, from Wave 2 step 10.

**Done when:** a test compiles a spec, generates a board from the same run, and asserts a value
present in `fullPrompt` appears on the board — and that a section absent from `fullPrompt` renders as
"not specified" rather than a default.

**Watch:** the caller in `worldsmith.ts` runs preview generation as a stage of the compile pipeline, so
`sectionRecords` is already in scope there. If you find yourself re-running the compiler inside the
preview service to get it, the plumbing is going the wrong way.

## 19c — Wave 2 step 14 residue

`buildLegacySectionsFromNewFormat` in `prompt-compiler.ts` (around L425) still carries the two
mislabeled mappings:

```js
materials_and_lighting:   payload.shared_prompt   // not materials
composition_and_content:  payload.front_prompt    // not composition
```

This only affects the legacy `sections` compat map, not `fullPrompt`, so no prompt is wrong because of
it. But anything reading `sections.materials_and_lighting` is reading print-and-bleed text under a
materials label. Either map them to the real fields or rename the keys to say what they hold.

**Done when:** the legacy section keys either carry the content their names claim, or are named for the
content they carry.

## Order

19c first (five minutes, no dependencies). Then 19a, because the migration and backfill want to land
on their own so any prompt change is attributable. Then 19b.

Do not combine 19a and 19b in one commit. One changes what goes into a prompt; the other changes what
a human sees when reviewing it. If a board looks wrong afterwards you want to know which.
