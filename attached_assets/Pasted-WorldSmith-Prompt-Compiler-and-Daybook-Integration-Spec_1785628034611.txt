WorldSmith Prompt Compiler and Daybook Integration Specification

You can share the following directly with Replit.

1. Project objective

Build a WorldSmith Prompt Compiler inside the existing Replit production service.

The compiler must:

Read a governed Production Specification from Notion.
Resolve all inherited design, canon, and production records.
Validate the record against CS-000: Production Payload Specification.
Assemble the exact prompt that will be sent to the image provider.
Calculate a deterministic prompt hash.
Create or update the corresponding Visual Asset.
Store complete generation provenance.
Submit the generation request through a replaceable provider adapter.
Store the generated file in Google Drive.
register or update the asset in Daybook using its stable Asset ID.
Return the Production Specification to the governed Artwork Review workflow.

The system must preserve the WorldSmith principle:

Inherit before generating. Missing dependencies must block the workflow rather than being guessed.

This aligns with the existing WorldSmith Automation Contract, which assigns orchestration, validation, prompt assembly, task creation, workflow transitions, retries, and provenance preservation to the WorldSmith Engine.

2. System boundaries
System	Responsibility
Notion	Governance, specifications, canon relations, approval state, workflow controls, Visual Asset metadata
Replit WorldSmith Engine	Inheritance resolution, validation, prompt compilation, provider orchestration, retries, logging
Google Drive	Authoritative storage for generated masters, versions, derivatives, and release files
Daybook	Stable asset identity, production-ready asset resolution, execution history, downstream lookup
Image provider	Image generation or transformation
Artwork Reviews	Human creative QA and approval

Do not create a separate Notion Generation Jobs database for the MVP. Operational run state belongs in the Replit run_repository; durable generation provenance belongs on the Visual Asset. This is consistent with the current automation design, which already specifies a persistent run ID, retries, idempotency keys, structured logs, and a run-status endpoint.

7. Canon validation

Canon validation must occur before a prompt is marked ready.

None
No Canon Record is required.
The asset must remain generic.
It must not introduce named people, places, institutions, dates, discoveries, ownership facts, or historical claims.
Supports Canon
The asset may express accepted themes, atmosphere, and material culture.
It must not define new facts.
Linked Canon Records, when used, must be Accepted.
Canon Reference
At least one appropriate Canon Record is required.
Every linked Canon Record used for generation must have Status = Accepted.
Visible text, identifiers, evidence marks, names, dates, locations, and symbols must be approved.
approved_text is required when readable narrative text is present.
Canon Defining
Generation remains blocked until the relevant canon decision is explicitly Accepted.
The compiler must not convert a proposal into production canon.

Proposed, Under Review, Superseded, Rejected, conflicted, malformed, or placeholder Canon Records must block compilation when the dependency requires canon.

9. Compiled Prompt Status behavior

Update the Production Specification using these values:

Status	Meaning
Not Compiled	No successful compilation has occurred
Ready to Compile	Required governed inputs appear complete
Compiled	Exact prompt was compiled and stored successfully
Validation Failed	A non-canon validation error blocks compilation
Requires Canon Review	Canon or visible-text approval blocks compilation

Suggested transitions:

Not Compiled
    ↓
Ready to Compile
    ↓
Compiled

Failure branches:

Ready to Compile → Validation Failed
Ready to Compile → Requires Canon Review

A compiled prompt should become stale if any governed source record changes. The initial MVP may detect this through a source fingerprint or by recalculating the prompt hash on demand.

10. Prompt hash

Calculate a deterministic SHA-256 hash.

Recommended hash input:

{
  "payload_version": "PP-1.0",
  "compiled_prompt": "exact compiled prompt",
  "negative_prompt": "exact negative prompt if separated",
  "generation_provider": "provider",
  "model_name": "model",
  "model_version": "version",
  "generation_settings": {}
}

Rules:

Normalize line endings to \n.
Preserve meaningful whitespace inside approved text.
Serialize settings using stable key ordering.
Store the lowercase hexadecimal SHA-256 result.
Do not hash timestamps, request IDs, costs, or generated filenames.

12. Stable asset identity

Use a stable logical Asset ID and a versioned filename.

Recommended pattern from the current automation design:

Asset ID:
WS-{WORLD}-{VOLUME}-{TYPE}{SEQUENCE}-{ROLE}

Example:

WS-WYC-V01-HP001-MASTER

Filename:

{WORLD}_{VOLUME}_{TYPE}{SEQUENCE}_{ROLE}_v{VERSION}.{EXT}

Example:

WYC_V01_HP001_Master_v001.png

Rules:

Asset ID is immutable.
Version starts at v001.
Never overwrite an approved or reviewed binary.
Version increments only when a new binary revision is intentionally requested.
Asset ID is the logical idempotency key.
Asset ID plus version is the binary idempotency key.

These rules are already part of the Replit production automation specification.

18. Failure and recovery rules

On failure, return:

{
  "status": "failed",
  "run_id": "uuid",
  "failed_stage": "canon_validation",
  "error_code": "CANON_NOT_ACCEPTED",
  "message": "Linked Canon Record WC-PUB-001 is Under Review.",
  "retry_safe": true,
  "recommended_action": "Link an Accepted Canon Record or complete canon review.",
  "created_resources": {
    "visual_asset_id": null,
    "drive_file_id": null
  }
}

Rules:

Do not silently substitute missing data.
Do not generate if required validation fails.
Do not approve artwork automatically.
Do not accept canon automatically.
Do not overwrite an approved binary.
Preserve successful intermediate work.
Retries resume from the last safe confirmed stage.
Re-running identical input must not create duplicates.

20. MVP scope

For the first working release:

Support only PP-1.0.
Support one Production Specification database.
Support one pilot Hero Paper.
Support one image provider.
Support compile-only and compile-and-generate.
Store the generated master in Google Drive.
Create or update one Visual Asset.
Record the complete provenance fields.
Upsert one stable asset into Daybook.
Create or route to an Artwork Review.
Demonstrate safe retry after at least three simulated failure stages.

Start with a deterministic test image if necessary. The existing Replit plan explicitly recommends proving orchestration and data integrity before replacing the test fixture with live image generation.

21. MVP acceptance criteria

The compiler is complete when one pilot Production Specification can be processed end to end and:

All required records are inherited automatically.
PP-1.0 validates correctly.
Missing fields return precise errors.
Canon restrictions block generation appropriately.
The exact Compiled Prompt is written to Visual Assets.
Prompt Hash is deterministic.
Generation Provider, Model Name, Model Version, Settings, Seed, Request ID, and Cost are stored when supplied.
The master file is stored in the correct Drive location.
The image is visible in Notion.
The Production Specification and Visual Asset are mutually linked.
Daybook resolves the asset by stable Asset ID.
Retrying does not create duplicate files, Visual Assets, or Daybook entries.
The asset proceeds to Artwork Review rather than being automatically approved.
An approved generation can later be reconstructed from its governed metadata.
Suggested Replit build instruction

Build this as an extension of the existing Replit Production Asset Automation & Daybook Sync service, not as a separate application. Use a modular architecture with notion_client, payload_parser, inheritance_resolver, validator, prompt_compiler, canon_validator, image_provider, drive_client, visual_asset_service, daybook_client, run_repository, workflow_service, api, and a lightweight control panel. Implement the compile-only path first, then provider generation, Drive storage, Visual Asset provenance, and Daybook synchronization.
